- 审阅范围：`D:\liuliu-minimap\东澳岛\data\` 下 5 份 xlsx + `餐厅菜单` 下 16 家店 56 个 PDF

| 潮汐咖啡 | 1 | **无效**：只是一张"扫码点餐"二维码海报（678×450），无菜品无价格 |

形态汇总：**团购套餐页截图 ≈ 32 页 / 实体菜单照片 ≈ 13 页 / 纯文字长截图 ≈ 10 页 / 无效 1 页**。

### 5.2 能否自动化抽菜品与价格

实测（rapidocr 轻量模型，抽样 3 页）：

| 样本 | 结果 | 判断 |
| --- | --- | --- |
| 东发海鲜酒家（长文字截图，按 bbox 原生分辨率裁切） | **16/16 段全对**：`洋葱炒牛肉：68元`、`韭菜花炒鱿鱼：68元`、`蒜香骨10块：88元`… | **可全自动落库**，置信度普遍 0.99 |
| 聚鲜楼（团购套餐页，切片 2× 放大后） | 12/12 段基本正确：`套餐内容 / 主食 / 椒盐虾 / 九菜花炒花甲肉 / 炒青菜 / 杂鱼冬瓜汤 / 送饮料 / 柠檬水 / 白米饭` | **可抽套餐内菜品清单**，但页面只有套餐总价 ¥198，无单品价；页面本身还带 `null` 脏值 |
| 洒哥海鲜餐厅 4（实体菜单翻拍） | 只识别出 2 段且是乱码（"`酒哥海鲜餐厅国国#店`"） | **不可靠**：反光、倾斜、分辨率低，必须人工校对或重拍 |

操作结论：

1. **纯文字长截图（10 页）**：最省力。按页面 bbox 取原生像素（不要用默认 72dpi 渲染，会糊成一条细线），切成 1500–2000px 高的条带送 OCR，可直接抽 `菜品名 + 价格`。注意 rapidocr 传**文件路径**时可能静默返回 0 段，传 `numpy array` 正常。
2. **团购套餐页（32 页）**：能抽"套餐名 + 套餐价 + 套餐内容清单"，但**没有单品价格**；部分条目价格为 `null`（截图源头就缺）。适合做成"套餐/推荐组合"字段，不适合做单品价目表。
3. **实体菜单照片（13 页）**：能抽一部分，但错字多（"牛肉王肠粉"应为"牛肉蛋肠粉"、"精动拾光"应为"精致拾光"），**必须人工校对**；且海鲜类大量是"时价"，抽不出确定价格。
4. 建议保留 `<店名>/<n>.pdf` → 反查 `餐饮表` 店名做外键；把 OCR 结果连同原图路径、置信度一起落库，低置信度进人工队列。

## 6. 导入 `spots` 集合的最小字段映射建议

现状（`cloudfunctions/initDongaoSpots/index.js`）：`spots` 只有 4 个字段 `map_name / amap_name / coords / location`，52 条全景点类 POI，个别人工重复（`观月亭`≈`观月台`、`东澳湾`≈`东澳湾沙滩`、`铳城`≈`东澳岛-铳城亭` 坐标完全相同）。

### 6.1 第一版最小可用映射（建议）

```
map_name    ← 项目 / 餐厅名称 / 住宿名称（清洗后；去掉"（东澳岛店）""-东澳岛万豪度假酒店"等后缀到独立字段）
amap_name   ← geocode 命中的高德标准名（为空时留空）
coords      ← 必须现补："lng,lat" 字符串（高德 POI 检索 + 人工抽检）
location    ← db.Geo.Point(lng, lat)   ← 依赖 coords，二者必须同时有值
--- 以下为新增内容字段（不参与地理查询） ---
type        ← spot | route | play | food | stay | shop   （来源：文件 + 类别列）
audiences[] ← 一级标签归一后（情侣/Z世代、亲子、银发/休闲、资深玩家）
needs[]     ← 二级标签
plays[]     ← 三级标签
bestTime    ← 最佳时段（原文）
duration    ← 游玩时长（原文，保留"约2小时""1-2天"等）
budget      ← 预算区间（原文，先不拆数值）
partySize   ← 适配人数（原文，后续再拆 min/max + 人群）
booking     ← 预订方式（原文）
address     ← 核心地点 / 位置（原文，作为 geocode 的输入）
openHours   ← 仅餐饮有，建议单独字段而不是塞进 bestTime
avgPrice    ← 仅餐饮人均，数值区间（解析出 min/max，解析不出保留原文）
sourceFile  ← 溯源：文件名 + sheet + 行号（强烈建议，方便复审）
verified    ← 实采状态（现有数据里已出现"已验证""待实采确认"两种口径）
```

### 6.2 落地顺序建议

1. **先补坐标**：把 5 份表的"名称 + 地址文本"合成一张 geocode 输入表（约 29+29+38+42+4 = 142 个实体，去重后约 110），用高德 POI 检索批量取坐标，人工抽检 10%。
2. **只把有坐标的实体写入 `spots`**：景点/路线/玩法/餐饮/住宿/购物市集 —— 预计 90 条左右。
3. **无坐标实体不进 `spots`**：活动类（购物表"活动"段 37 条，其中 11 条是酒店住客权益）、研学线路、夜间玩法等，建议单独建 `activities` 集合，用 `spotName` 关联父级 spot（现有 `dongaoCards` 已经是"spotName + mission"的挂载结构，可复用）。
4. **先关联、后新增**：景点表里能对上现有 52 个 spot 的约 10 条（婚礼堂、蜜月阁、滨海栈道、月牙环、风车山、求子泉、铳城、山海经书屋、万山海洋生物科普馆、东澳海关遗址），优先按 `map_name` 补字段而不是新增记录；住宿/餐饮在现有 52 条里**完全没有对应 POI**，属于纯新增。

### 6.3 客群标签归一（必须做，否则筛选会碎）

同一概念在不同文件里有 2–3 种写法：

- 情侣类：`Z世代/情侣客群`（景点 13）· `Z世代/情侣`（景点 8 / 住宿 24 / 购物 31）· `情侣客群`（餐饮 38）
- 亲子类：`亲子客群` · `亲子`
- 银发类：`银发/休闲` · `银发/休闲客群` · `银发客群` · `银发`
- 硬核类：`资深玩家/硬核探索客群` · `资深玩家/硬核探索` · `资深玩家`

分隔符也不一致：**餐饮全用全角"，"，其余 4 份用"、"**；而标签内部本身含"/"（"Z世代/情侣"），**不能按"/"切分**。

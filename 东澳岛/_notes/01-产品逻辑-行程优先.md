# 东澳岛内容生产与交互逻辑：从"随机卡片"到"行程骨架 + 现场任务"

> 产品设计视角。基于现有代码事实（`miniprogram/pages/dongao`、`cloudfunctions/dongao*`）与本轮采集数据（6 份 docx / 5 份 xlsx）做推演，不是拍脑袋。
> 前置结论数据：52 个点位经纬度跨度仅 **2.97km × 2.22km（对角 3.71km）**；从码头东澳湾出发，最近的 10 个点全在 **331m** 内，第 1 近与第 6 近只差 **202m**。也就是说，现有 `geoNear` 按距离排序，在小岛上几乎等于随机排序。

---

## 0. 一句话结论

游客要的不是"一个随机的任务"，也不是"一份排死的行程"，而是**"今天怎么过"的确定感 + 现场的自由度**。

正确形态：**先给一张可执行的行程骨架（人编排、规则排），再在执行现场长出任务卡（AI 生成）**。

配套判断：**客群只该决定"去哪、待多久"，不该决定"做什么动作"。** 现有数据里的三级标签（"游客在这个项目能做什么"）本来就是点位属性，和客群无关；客群只是筛选与排序权重。

---

## 1. 游客在岛上的真实处境

先把场景摆清楚，方案才有讨论基础。

### 1.1 四个客观约束

| 约束 | 事实 | 产品含义 |
| --- | --- | --- |
| **时间被船班切碎** | 上岛/离岛时间是硬约束，实际可玩 3–8 小时 | 产品必须能"倒推"时间，而不是无限推荐 |
| **空间被接驳车组织** | 岛上观光车分 1/2/3 号线 + 固定站序 | 点位之间的"怎么去"比"去哪里"更影响体验；线路站点是天然的信息架构 |
| **岛太小，距离无意义** | 52 个点全在 3.7km 对角范围内，最近 10 个点相距 <331m | 现有"按距离推荐最近景点"是**伪需求**，用户感知不到 200m 的差别 |
| **体验被时刻改写** | 潮汐、日晒、日落、排队、营业时间 | 同一个点 9:00 / 14:00 / 17:30 是三种体验，"此刻"比"这里"重要 |

### 1.2 三个心理焦虑

岛上游客的问题不是"没内容"，而是：

1. **怕错过**——哪些是必须去的？我是不是漏了那个最好看的点？
2. **怕消耗**——会不会很累、很晒、排很久、带老人小孩走不动？
3. **怕时间不够 / 错船**——现在几点，还够去几个地方，什么时候该往回走？

**"随机卡片"回答不了这三个问题，行程卡正好能回答。**

### 1.3 两个决策场景

- **规划期**（船上/码头，约 5 分钟）：想被安排，不想做十道选择题。此时需要"给答案"。
- **执行期**（岛上，边走边改）：想保留自由，累了想坐、饿了想吃、下雨想躲。此时需要"改得了"。

任何方案如果只覆盖其中一个场景，都会别扭。

## 2. 现有卡片逻辑的心理账

### 2.1 它做对的

- 门槛极低：点一下就有内容，不用做选择；
- 有惊喜感：像抽卡，适合"随便走走"；
- 单点生成质量可控，AI 失败也只毁一张卡；
- 与记录页打通，能形成纪念记录。

### 2.2 它的问题

| 问题 | 机制 | 用户感受 |
| --- | --- | --- |
| 老虎机效应 | 每换一个地点就重新生成，卡与卡之间没有关系 | "我一直在抽卡，但没有'今天玩完了'的感觉" |
| 无时间预算 | 卡片不告诉你"这里要待多久""下一站还来不来得及" | 玩到一半才发现时间不够 |
| 动线可能折返 | `onNewSpot` 只是把当前点加进 `eliminatedNames`，排序仍靠 `geoNear` | 来回走 200 米，路线碎 |
| 任务无因果 | mission 由"点位 + 天气 + 潮汐"生成，与上一站、下一站无关 | "做完了，然后呢？" |
| 历史是假的 | 客户端从不读 `dongaoCards`，历史只在内存 | 冷启动后卡片全丢，无法回看 |

### 2.3 它的合理适用场景（不要一刀切删掉）

- 在岛时间 **≤ 3 小时**（晚班船、转岛、临时起意）；
- 已经玩过一轮、只想再找个点发呆；
- 只想"随便走走"，不想被安排。

**结论：单点卡片不该是默认主干，但应保留为"短时/随意"模式。**

## 3. 方案 1 评估：先选身份，再选需求，再喂标签生成任务

### 3.1 对的部分

- 标签体系确实是资产，客群 × 需求 × 玩法确实该进入推荐逻辑；
- 需要一点个性化，否则 4 类客群拿到同样的内容；
- "懒人式卡片 + 可换"的交互手感是对的，不应推翻。

### 3.2 错的部分（三个关键错位）

**① 把内部生产维度当成了用户界面。**
"吃 / 购物 / 景点 / 住宿"是《实施方案》第四节的分工维度（食→情侣组、住→银发组……），是**内容团队怎么分工采集**，不是游客怎么决策。把它做成首屏选择，等于把数据库结构暴露成表单。

**② 这四类其实是"时间触发"，不是"顶层品类"。**
游客不会决定"今天我主要需求是住宿"——住宿是既定事实（订了哪家）；"吃"发生在饭点；"购物"多发生在离岛前；"景点"发生在白天。用时间轴组织才是真实心智，用类目组织是整理者心智。

**③ 客群喂 AI 生成任务，会让任务变成"人设表演"。**
同一个点（比如南沙湾），情侣要的是"日落合影"，银发要的是"坐着看海、有遮阴"，亲子要的是"孩子能玩沙"。差别在**停留方式、时长、体力**，而"具体动作"其实高度共通（看、听、拍、坐）。现有 prompt 已经证明：给同一点位 + 天气 + 潮汐就能生成可执行的动作，客群加进去的价值主要在语气和难度，不在动作本身。

**④ 身份自评不准且问卷感强。**
用户不是"一个客群"，而是"两个人 + 第一次来 + 想轻松 + 有点想拍照"。让他在一级标签里选自己，既有心理抗拒，也选不准。

### 3.3 怎么改造成可用的

保留它的内核，但**下沉**：
- 客群 → 变成"行程模板的选择/排序权重"，不进首屏；
- 需求 → 变成"时间块填充规则"（饭点找吃、下午找遮阴、日落找西向）；
- 三级标签 → 变成"点位玩法库的原子条目"，是任务生成的素材，不是用户选项。

如果一定要保留用户选择，**压缩成 2 个问题**（见 §5.2），不要两级标签问卷。

## 4. 方案 2 评估：一次生成整条游玩路线

### 4.1 对的部分

- 方向正确：先规划再执行，符合"今天怎么过"的真实需求；
- 解决碎片感与动线问题；
- 一次投入换来整体叙事，打卡完整性更强。

### 4.2 错的部分（四个风险）

**① 一次性 AI 生成整条路线不可控。**
路线质量 = 站点顺序 × 时长分布 × 体力曲线 × 交通衔接 × 营业/潮汐约束。AI 能写文案，但不擅长排班；一次生成 4 段，每一段都可能不合理，且用户很难指出"哪里不对"。

**② 首次信息不足，无法一次决定。**
刚上岛的人不知道哪个点好玩、走起来多累。让他一次确认整天行程，等于让他提前承担决策风险。

**③ 计划刚性 = 挫败感。**
船班延误、排队、下雨、孩子走不动，都会让"计划"变成"没完成的任务"。产品要避免制造"我没按计划走"的负罪感。

**④ 冷启动成本高，失败代价大。**
生成 4 段要更长的 prompt 与更多 token、更长等待；失败一次，全盘重来。且岛上信号一般，长链路在线生成风险高。

### 4.3 怎么改造成可用的

**拆成"确定性"和"不确定性"两层**：

- **排路线**：不要 AI，用**人工编排的模板 + 规则校准**（客群 × 时长 × 上岛时间 → 时间块序列）。确定性、秒出、可解释、可测试。
- **写内容**：AI 只负责两件事——给每段写一句"为什么现在是来这里"，以及到点后生成"此刻任务卡"。

> 一句话原则：**确定性用规则，不确定性用 AI。** 路线是班次表，任务才是灵感。

## 5. 推荐方案：行程优先，任务现场生成（Plan-then-Play）

### 5.1 内容分三层

| 层 | 谁生产 | 内容 | 特点 |
| --- | --- | --- | --- |
| **点位层** | 数据团队 + 半自动 | 每个点：能做什么（三级玩法条目）、待多久、体力、遮阴/休息、人均、几点最合适、从哪站下 | 静态、可审核、复用 12 字段 |
| **路线层** | 人编排（4–8 套模板） | 客群 × 时长 → 时间块序列：每段站点 + 交通 + 主玩法 + 备选 + 一句话理由 | 确定性资产，出错可人工修 |
| **此刻层** | AI（现有 dongaoGenerate） | 到了这个点、这个时刻，具体做哪一件小事 + 提示 + 安全语 | 即时感、有惊喜、失败了不影响行程 |

关键点：**任务不再是"随机卡"，而是"这一段的执行细则"**。它天然有上下文（上一站、已打卡、当前时间、天气），生成质量反而更高。

### 5.2 首屏只问两个问题

1. **和谁**：一个人 / 两个人 / 带小孩 / 带长辈（4 选 1，决定模板与体力上限）；
2. **在岛上多久**：半天 / 一整天 / 住一晚（3 选 1，决定段数与节奏）。

第三个信息**不问**，用现有数据推断：`walkRecords` 里如果有 `walkMode='dongao'` 的历史 → 默认"回头客版"（小众 + 错峰）；没有 → 默认"首访版"（经典必看）。

默认值直接出卡，用户不需要点"生成"。这就是懒人设计：**先给答案，只在你不同意时修改。**

### 5.3 今日行程卡（核心界面）

```
┌────────────────────────────────────┐
│ 今天在岛上一整天 · 两个人            │   ← 可点，改了重排
│ 首访 · 经典动线        [换一版]     │
├────────────────────────────────────┤
│ 09:40  ① 东澳湾码头                │  已到
│        下船 → 2号线 2 站 → 南沙湾    │
│ 10:10  ② 南沙湾沙滩                │  进行中
│        沙滩散步 · 拍一张有海平线的照片 │
│        约 1h · 轻松 · 免费          │
│        [到了] [换这段] [跳过]        │
│ 12:00  ③ 海鲜午餐（2 选 1）         │
│ 13:30  ④ 蜜月阁 + 婚礼堂（出片）     │
│ 15:30  ⑤ 书屋/咖啡（躲太阳）        │
│ 17:00  ⑥ 南沙湾看日落 → 回码头      │
└────────────────────────────────────┘
```

每段包含六件事：**时间 / 站点（几号线第几站）/ 怎么去 / 做什么 / 多久多累多少钱 / 为什么现在来**。
前五项来自模板，第六项来自 AI 或模板文案。

### 5.4 四个动作

| 用户动作 | 系统行为 |
| --- | --- |
| **到了** | 调现有 `dongaoGenerate`（注入：模板段落 + 点位玩法 + 当前时间/天气/潮汐 + 已打卡）→ 出"此刻任务卡" |
| **换这段** | 只换这一段：从该段的备选点位里换（保证不动整体动线） |
| **换一版** | 换整套模板：经典版 / 轻松版 / 出片版 / 慢游版 / 硬核版 |
| **我累了 / 饿了 / 下雨了** | 局部重排剩余段：删费腿点、插附近餐馆、换室内点（书屋/博物馆/餐厅/酒店），不推翻已完成的段 |

这就是"自由度"的正确位置：**不是每张卡都重抽，而是随时改计划。**

### 5.5 结束与闭环

走完 → 行程卡（已打卡的段落点亮）→ 一键生成"纪念卡"进入足迹页。
与现有主线的衔接几乎零成本：`themeSnapshot.missions` 从 1 条变成 N 条，`walkMode:'dongao'` 不变，**记录页/足迹页/卡册统计本来就支持多 mission**。

## 6. 为什么这个更贴合心理预期

| 心理需求 | 方案 1（标签卡片） | 方案 2（一次性路线） | 推荐方案 |
| --- | --- | --- | --- |
| 怕错过 → 要确定感 | ✗ 随机给点 | ✓ 但可能排错 | ✓ 模板保证必看 + 备选兜底 |
| 怕消耗 → 要成本透明 | ✗ | △ 一次给完，难改 | ✓ 每段标注时长/体力/人均 |
| 怕错船 → 要时间锚 | ✗ 无时间轴 | ✓ | ✓ 时间轴 + 下一段提示 |
| 要自由 → 怕被绑死 | ✓ 但碎片 | ✗ 刚性 | ✓ 局部重排 |
| 要成就感 → 叙事完整 | ✗ | ✓ | ✓ 逐段点亮 → 纪念卡 |
| 首屏负担 | 高（问卷） | 高（一次决定） | **低（默认答案）** |

三个"更贴合"的具体点：

1. **决策次数从 N 次降到 1 次**：默认给答案 + 微调，符合"懒人设计"又不剥夺控制感（progressive disclosure）。
2. **任务从"内容消费"变成"行为触发器"**：任务挂在"这一段的点位 + 此刻"上，用户会真的去做，而不是滑过去。
3. **把"岛上时间"变成了产品结构**：时间轴本身就是导航，用户随时知道"现在该干嘛、还剩多少"。

## 7. 内容生产逻辑要跟着改（回答"最贴合实际需求"的落点）

### 7.1 从"资料属性"到"可用性属性"

现在 12 字段是**资料属性**（这是什么、在哪、多少钱、适合谁）。产品需要的是**可用性属性**：

| 资料属性（已有） | 可用性属性（缺） | 决定什么 |
| --- | --- | --- |
| 项目、标签、预算 | **几点最合适** | 这段放上午还是傍晚 |
| 游玩时长 | **待多久**（含进出/排队） | 一天能塞几段 |
| 适配人数、人群 | **体力等级**（轻松/中等/费腿） | 带娃带老人能不能去 |
| 核心地点 | **几号线第几站 + 从上一站怎么来（步行/车/几分钟）** | 动线能不能接上 |
| 周边情况（遮阴/洗手间/商户/休息点） | **雨天/暴晒替代方案** | 天气突变时能不能救场 |
| 预订方式 | **营业时间 + 是否要排队/预约** | "现在去来不来得及" |

### 7.2 内容生产的新单位

现在的单位是"项目 × 客群 × 玩法"。建议改成 **"时间段 × 站点 × 客群"**：

- 4 个客群 × 2 种时长（半天/整天）= 8 套行程模板，**先做 4 套**（情侣出片、亲子轻松、银发慢游、硬核环岛）；
- 每套模板 = 4–6 段，每段绑定 1 主点 + 1 备选；
- 每段的内容卡 = 1 条"为什么现在来" + 1 条任务 + 1 条提示 + 1 条安全语。

**工作量对比**：一次性路线方案要为"每个客群 × 每天"实时生成；模板方案是**确定性资产**，4 套模板 + 点位库即可覆盖绝大多数首访游客，后续按数据迭代。

### 7.3 必须先补的 6 个字段（按性价比排序）

1. **站点序号**（1/2/3 号线第几站）——决定动线，最高优先；
2. **从上一站怎么来 + 几分钟**——决定"排不排得下"；
3. **建议时长**（含排队缓冲）——决定一天几段；
4. **体力等级**（轻松/中等/费腿）——决定带娃带老人能否去；
5. **最佳时段**（可拆成时间段数组）——决定上午/午后/日落；
6. **遮阴/休息点/洗手间**——决定银发与亲子能不能落座。

文档里没写、但一定得补的 3 个：**营业时间**、**雨天替代**、**离岛船班/末班车**。

## 8. 分期落地（对应"稍加修改"）

| 期 | 内容 | 工期 | 依赖 |
| --- | --- | --- | --- |
| **P0** | 4 套行程模板（静态 JSON）+ 行程卡页面 + "到了"触发现有的 `dongaoGenerate` + 结束生成纪念卡（record 已支持多 mission） | 5–7 天 | 点位先补站点/时长/体力 3 个字段即可 |
| **P1** | 换这一段 / 换一版 / 累了饿了下雨的局部重排 + 运行时时长与体力提示 | +5 天 | P0 数据 |
| **P2** | 回头客版、动态排队/船班、按匹配度的个性化排序、多日行程 | +2 周 | 真实使用数据 |
| 保留 | 短时/随意模式 = 现有单点卡片（≤3h 或用户主动选"随便逛逛"） | — | — |

工程上几乎不新增云函数：模板是静态数据，`dongaoGenerate` 只需改上下文（多传段落/时段/已打卡），`record` 侧本来就是多任务。

## 9. 怎么验证（别只靠感觉）

上岛陪走 8–10 组真实游客（情侣/亲子/银发各 2–3 组），只看 4 个指标：

1. 看了行程卡后**改动次数**（0 次 = 默认答案对了；≥3 次 = 模板不对）；
2. **按时长走完的段数 / 总段数**（模板时间估得准不准）；
3. 点"到了"后 **30 分钟内打卡率**（任务是不是真的被做了）；
4. **卡住的地方**（找不到入口 / 等不到车 / 没座位 / 排太久）→ 直接变成点位库的"周边情况"字段。

这四个指标能同时验证模板、任务、字段三件事，比"用户说好不好"可靠。

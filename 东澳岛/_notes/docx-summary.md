## 二、逐份摘要

### 1. 东澳岛AI玩法内容生产与交付实施方案_优化版

- **定位**：把“游客是谁 → 想要什么 → 在哪个点位怎么玩”变成一条可交付给 AI 的标签流水线。
- **读者**：4 个客群小组（执行）、技术团队（消费方）、项目负责人（交付验收）。
- **章节骨架**：一、项目整体构想（五层内容链条）→ 二、内容生产逻辑（5 步表格）→ 三、游客画像与任务分组（4 客群 × 组员 × 二三级标签 × 待验证项）→ 四、玩法挖掘范围（食/住/游/购+活动 4 维度分工）→ 五、标准化采集字段（12 字段）→ 六、上岛实采与验证安排（4 阶段）→ 七、最终交付标准（4 项）。
- **关键结论**：
  - 核心方法是五层链条：**客群标签 → 需求标签 → 玩法标签 → 资源点位 → 验证信息**；先线上调研出初版，再上岛验证。
  - 客群固定为 4 类：Z世代/情侣、亲子/自然教育、银发/休闲、资深玩家/硬核探索，是 AI 判断用户身份的**一级标签**（可多选，但批注要求体现匹配度）。
  - 资源按**食/住/游/购+活动**四类梳理，每类落到人（食→情侣组，住→银发组，游→亲子组，购+活动→资深玩家组）。
  - 最终交付 4 样东西：结构化数据库（可直接导入、尽量避免二次清洗）、4 条小红书图文、素材包（照片/视频/路线记录/验证信息）、复盘建议（哪些玩法可立即上线）。

### 2. 第二阶段任务说明(1)

- **定位**：填表用的**标签词典 + 字段示例 + 分工**，是实施方案第三节/第五节的落地补充。
- **读者**：各小组填表人（尤其需要照着批注改口径的人）。
- **章节骨架**：二级需求标签梳理（4 客群 × 1 张总表：二级标签 / 二级标签定义 / 三级玩法标签）→ 字段采集示例及说明（以“山海经书屋”为示例，12 字段）→ 分工（食/住/游/购+活动）。
- **关键结论**：
  - 二级标签是“需求”，三级标签是“具体玩法”，一句话可记：**二级答“为什么去”，三级答“去了具体做什么”**。
  - 每个二级标签都给了定义句，便于统一口径（如“挑战：追求有体力、技术、胆量或风险门槛的硬核体验，获得刺激感、征服感和完成感”）。
  - 6 条客户批注直接改写了字段口径（见 §3.4），其中 4 条是硬要求：应填尽填、按客群兴趣匹配而非罗列人群、三级标签写“游客能做什么”、核心地点写“观光车几号线第几站”。
  - 示例行大面积留空（周边情况/最佳时段/游玩时长/预算/人数/预订/待验证项），说明**示例只是格式示范，真实值必须上岛采**。

### 3. 东澳岛亲子研学攻略-内容框架与任务分工书

- **定位**：亲子组要产出的**小红书攻略写作模板**（孩子能玩、家长省心、全家安全）。
- **读者**：亲子组组员（赵婴、王子琦、徐铭晗 一组）。
- **章节骨架**：一、任务目标与客群定义 → 二、内容框架（2.1 开篇定调 → 2.2 四大体验模块 → 2.3 行程与配套设计 → 2.4 安全与避坑）→ 三、交付物。
- **关键结论**：
  - 全文递进逻辑：亲子内核（Why）→ 体验模块（What）→ 行程落地（How）→ 安全便利（Proof）。
  - 四大模块：①参与互动 ②教育科普 ③安全与省心 ④舒适配套。
  - 行程建议是**可结构化**的：2 天 1 夜轻松版 / 3 天 2 夜研学版；每天一个主题（沙滩自然日 / 海岛文化日 / 亲子挑战日），**每天 2 个主点位 + 1 段自由活动**，上午下午各一段，留午休。
  - 每个项目必须标注：孩子能亲手做什么、家长怎么配合、耗时、适龄（幼儿/学龄/青少年三档替代玩法）。
  - 这也间接定义了小程序要做的事：亲子页面的任务应以“天 + 主点位 + 自由活动”为单位，而不是单点单任务。

### 4. 东澳岛Z世代情侣攻略-内容框架与任务分工书

- **定位**：情侣组小红书攻略模板（出片 + 浪漫 + 省心）。
- **读者**：Z世代/情侣组（廖逸扬、路凯雯、周润枝）。
- **章节骨架**：一、任务目标 → 二、内容框架（2.1 开篇一句话种草 → 2.2 四大体验模块 → 2.3 行程节奏设计）→ 三、交付物。
- **关键结论**：
  - 开篇要直接给 **3 个必打卡“铁三角”组合**，让读者 3 秒决策（原文举例：1314 米滑道的速度与激情、山海间的书香约会、南沙湾的日落承诺）。
  - 四大模块：①出片指南（机位 + 最佳时间 + 构图 + 穿搭配色，白/红长裙更出片）②浪漫互动（每个点位给一句“互动动作建议”）③小众私密（怎么避开人流：错峰时间、小众入口）④慢享放松（明确建议停留时长）。
  - 行程要写“几天几夜”，但**具体天数未定**（原文只写“需包含 几天几夜的行程安排”）。
  - “互动动作建议”和“停留时长”这两项是文案语料的关键，也是小程序任务卡可以直接复用的字段。

### 5. 东澳岛资深玩家攻略-内容框架与任务分工书

- **定位**：资深玩家组小红书攻略模板，反“打卡式流水账”，要专业度/探索感/硬核。
- **读者**：资深玩家组（雷璧蔓、刘智、常程超）。
- **章节骨架**：一、任务目标 → 二、内容框架（2.1 导言：为什么是东澳 → 2.2 四大维度 → 2.3 空间层次感构建 → 2.4 生存指南与专业背书）→ 交付物。
- **关键结论**：
  - 四大维度：①硬核挑战（技术难点/装备/风险）②野性探索（非景区、GPS 轨迹、怎么找入口）③沉浸与修行（单点停留 2 小时以上）④专业视角（钓点选择、摄影参数）。
  - **路线设计要三种视角叠加**，这是全文最明确的多路线要求：
    - 垂直：海平面（浮潜）→ 海岸线（徒步）→ 山脊线（风车山）
    - 时间：清晨 5-7 点 → 正午 11-14 点 → 黄昏 17-19 点
    - 冷热：热门点（蜜月阁）+ 冷门野路（海关古道深处）穿插
  - 写作硬规则：去网红化（禁用“小镰仓”等词，每个点必须有硬核理由）、数据化（徒步写里程与爬升、潜水写能见度与水流、摄影写机位朝向）、专业术语 + 可操作建议。
  - 风险内容（暗流、晒伤、潮汐表、LNT）对小程序任务卡意味着必须有“安全提示/风险等级”字段，比现有 safetyNote 更重。

### 6. 东澳岛银发休闲攻略-内容框架与任务分工书

- **定位**：银发组小红书攻略模板，核心是“省力、舒适、有尊严”。
- **读者**：银发组（杨喜珠、鲁红艳、周建阳）。
- **章节骨架**：一、任务目标与客群定义 → 二、内容框架（2.1 开篇定调 → 2.2 四大模块 → 2.3 节奏与便利设计）→ 三、交付物。
- **关键结论**：
  - 递进逻辑：慢游内核（Why）→ 体验模块（What）→ 康养落地（How）→ 便利保障（Proof）。
  - 四大模块：①慢游低体力路线（每点标步行距离、座椅/遮阳/无障碍、排队情况）②治愈康养（强调“时长 + 节律”，单点停留 1 小时以上，避开日晒高峰）③人文与美食（历史要讲故事；美食要写价格区间、品类、位置）④社交与私密。
  - 行程模板明确：**3 天 2 夜深度慢游为主，2 天 1 夜为备选**。
  - “步行距离 + 无障碍 + 座椅”这套字段，是把“低体力”变成可计算筛选条件的唯一路径，小程序若支持银发客群必须落这些字段。

### 3.2 推荐路线 / 动线

文档里出现 4 种“路线”概念，粒度不同，别混：

1. **接驳交通线路（最刚性）**：岛上接驳车已分 **1 号线、2 号线、3 号线**，批注要求每个点位写“在几号线的第几站”。示例行里山海经书屋的“核心地点”就写的是“观光车1号线”；“3号线游览”出现在性价比玩法的三级标签里。
2. **资深玩家的三视角路线**：垂直（浮潜/徒步/风车山）、时间（清晨/正午/黄昏）、冷热（蜜月阁 vs 海关古道）。
3. **亲子/银发的串联动线**：观光车/电瓶车串联，步行段短而平；亲子“每天 2 主点位 + 1 段自由活动”，银发“3 天 2 夜慢游为主模板、2 天 1 夜备选”。
4. **情侣的节奏动线**：按四大模块排“几天几夜”，不强调地理顺序，强调错峰与停留时长。

### 3.5 交付物与验收标准

**交付物（实施方案第七节，4 项）**
1. 结构化数据库：字段统一、标签清晰、**可被技术团队直接导入 AI 系统，尽量避免二次清洗**。
2. 小红书宣发包：**4 条图文**，突出不同客群的真实玩法和可视化场景。
3. 素材包：按点位归档照片、视频、路线记录、现场验证信息，便于持续更新。
4. 复盘建议：哪些玩法适合立即上线，哪些要等商户/交通/预约/安全条件完善。

**各攻略书自己的交付物**：一篇小红书笔记（年轻有网感 / 亲切有温度），配封面图与机位示意图。

**验收标准（文档未写“验收”二字，以下是文中可直接落成验收的条目）**
- 字段完整、命名与标签口径统一（“统一命名和标签口径”是复盘后阶段的明确动作）。
- 岛上现存项目“应填尽填”；删除不可推荐或证据不足的内容（复盘后阶段）。
- 每条数据能被 AI 直接引用，不需要技术团队二次清洗。
- 4 条小红书图文全部产出；素材按点位归档。

> 缺口：**没有任何量化验收指标**（如字段完整率 ≥ x%、每个客群最少点位数、每条线路最少站点数）。这是需要补的。

## 四、这些文档要求“东澳岛”页面做哪些改动

### 4.1 现状（代码事实）

当前东澳岛页 `miniprogram/pages/dongao/` 只有一条很窄的链路：

1. 手动定位 / 选一个模拟景点（`dongao.js` 里硬编码 50 个点位的 `DEBUG_SPOTS`）。
2. `dongaoRecommend` 按 GPS 距离返回最近 20 个 spot（`cloudfunctions/dongaoRecommend/index.js`），字段只有 map_name / amap_name / coords / lat / lng / distance / sortRank。
3. 取 spots[0] 调 `dongaoGenerate`，AI 只生成 **1 条 mission（14-28 字）+ tips（12-24 字）+ safetyNote（8-16 字）**（prompt 见 `cloudfunctions/dongaoGenerate/index.js` 302-328 行）；上下文来自云存储的 `dongao-content/<景点名>.json`（task1_environment、task3_sensory_play）+ weather.json + tide.json + guide.md。
4. 卡片可左滑“换个任务/换个地点”、右滑看历史，历史来自内存 historyCards + 云端 `dongaoCards`。
5. 点“开始这次漫步”写 walkMode: 'dongao'，missions: [card.mission]（**单条任务**）进记录页。

即：**单景点推荐 + 单条 AI 任务 + 单条记录**。没有客群、没有行程、没有路线、没有多任务、没有点位详情、没有预订信息。

### 4.2 文档要求页面必须新增的能力

| 新增能力 | 文档依据 | 对页面的具体要求 |
|---|---|---|
| **多客群（4 类）** | 实施方案第三节 / 第二阶段标签词典 | 入口要有客群选择（Z世代情侣 / 亲子 / 银发 / 资深玩家），或根据用户画像默认；任务文案、推荐点位、提示语全部随客群切换 |
| **多任务 / 任务组** | 4 份攻略书都按“四大模块”组织；亲子“每天 2 主点位 + 1 段自由活动” | 任务卡从 1 条改为**按模块/按天分组的任务清单**（一条主线任务 + 若干可选任务）；每条带玩法标签（三级标签） |
| **多日行程** | 情侣“几天几夜”、亲子 2 天 1 夜/3 天 2 夜、银发 3 天 2 夜为主 2 天 1 夜备选 | 需要行程结构：dayIndex + 时段（上午/下午/傍晚/夜间）+ 每段点位 + 停留时长 + 用餐/住宿，页面能做“第 1 天 / 第 2 天”切换 |
| **路线 / 动线** | 批注“观光车 1/2/3 号线第几站”；资深玩家垂直/时间/冷热三视角 | 点位的**线路 + 站点序号**字段；至少支持“按线路浏览”和“按一条推荐动线串起来看”，而不是只按距离推 |
| **点位详情字段** | 实施方案 12 字段 / 批注补充 | 卡片需展示：最佳时段、耗时、预算区间、适配人数、周边情况（交通/遮阴/洗手间/商户/休息点/安全提示）、预订方式；现有卡片只有 mission/tips/safetyNote/distance |
| **匹配度（客群 × 项目）** | 批注：要考量“项目属性与客群兴趣的匹配度” | 需要主/次匹配客群字段，页面可据此过滤或排序，而不是全量罗列 |
| **预订/票券信息** | 字段 11“预订方式”（现场/电话/小程序/酒店前台/无需预约） | 最低限度：点位卡展示“怎么预订”；文档**没有**要求票券核销、库存、下单 |
| **任务与攻略同源** | 交付物要求数据库“可被 AI 直接导入” | 页面消费的数据应与 4 篇小红书攻略用的是**同一套结构化字段**，避免两套口径 |

### 4.3 文档没要求、但对比项里提到的能力（需产品决策）

- **票券 / 核销 / 订单 / 支付**：全文 0 次出现“票”“门票”“核销”“订单”，只有“预订方式”和“渔民私厨预约”。现在做票券属于超范围。
- **收藏**：全文 0 次出现“收藏”。要做需要产品侧另行决定。
- **分享**：攻略书要求产出小红书笔记，但那是**内容团队对外投放**，不等于小程序内的分享功能。
- **社区/UGC**：文档没有任何用户发帖、评价、晒图的产品设计。

### 4.4 数据结构与接口影响（建议，非文档原文）

1. spots 集合扩字段：audiences[]（一级）、needs[]（二级）、plays[]（三级）、matchLevel（主/次匹配）、line（1/2/3 号线）、stationNo（第几站）、bestTime、duration、budget、partySize、booking、surroundings{traffic,shade,toilet,shops,rest,safety}、verifyNotes。
2. 新增行程/路线数据：routes（线路 → 站点序列）与 itineraries（客群 → 天数 → 时段 → 点位）。
3. dongaoGenerate 输出需要扩展：从 {mission,tips,safetyNote} 变为 {audience, missions[], tips[], safetyNote, booking?}；prompt 里“14-28 字单任务”的约束要随客群/模块放宽。
4. dongaoCards 需要记录客群和任务组，否则历史卡片无法按客群回看。
5. 现有“按距离推荐 20 个点”与“按线路/行程推荐”是两套排序逻辑，需要明确谁优先。

### 4.5 落地优先级（建议）

1. **先落数据**：12 字段 + 线路站序 + 匹配度先入库，页面才有东西可展示。
2. **再做客群入口 + 多点位详情卡**（改动小、见效快，不破坏现有单任务链路）。
3. **再做多任务/行程**（需要记录页一起改：themeSnapshot.missions 从 1 条变多条，walkMode 可能要新增或扩展）。
4. 票券/收藏留到产品确认后再做。
